- Check: `npm run check` (Biome, oxlint, TypeScript, Vitest). The judge session runs the checks listed here.
- Lint: oxlint with the anti-slop plugin, vendored in `tools/oxlint/anti-slop/` (see its `UPSTREAM.md`). Biome only formats and sorts imports. Outside data is checked with TypeBox schemas, not `typeof`.
- `docs/spec.md` is the behaviour spec: output lines, exit codes, run directory layout, commit message format. Update it in the same change as the behaviour. `README.md` has only the install, a short usage and development; keep it short.
- Two npm packages come from this repository: `@vzlentin/workflows`, with the `workflows` command, and `@vzlentin/pi-workflows`, the Pi extension in `pi/`, with the `workflow` tool. They are released together, with one version. `pi/package.json` has `pi.extensions`, the keyword `pi-package`, `peerDependencies` and no `dependencies`. The setup of a global install (`src/setup.ts`) runs `pi install npm:@vzlentin/pi-workflows@<version>`.
- Release: release-please (`release-please-config.json`, `.release-please-manifest.json`) keeps one release PR open on `main`, titled `release: <version>`, with the version and `CHANGELOG.md` from the Conventional Commits since the last release. Merging a feature PR releases nothing. Merging the release PR makes `.github/workflows/publish.yml` create the tag and the GitHub release, and publish the version to npm with trusted publishing. `pi/package.json` follows the version through `extra-files` in `release-please-config.json`. The publish job publishes both packages, the root and then `pi/`, and skips each version that npm already has. Before 1.0, a breaking change bumps the minor and `feat` or `fix` the patch; a `Release-As: <version>` footer in a commit sets the version. release-please opens the release PR with the token of a GitHub App (the variable `RELEASE_APP_CLIENT_ID` and the secret `RELEASE_APP_PRIVATE_KEY`), so the check runs on it; without the app it falls back to `GITHUB_TOKEN`, whose PR runs no check. Do not change `version` by hand and do not run `npm publish` by hand. When a change needs a new `@vzlentin/harness`, release harness first and wait until npm shows it: `npm ci` fails before.
- The root package publishes `dist/`, `workflows/`, `prompts/`, `agents/` and `scripts/postinstall.js`. `prepack` builds `dist/` with `tsconfig.build.json`; `dist/` is not in Git. The checkout runs from source with Node type stripping (`node src/cli.ts`), so keep `src/` runnable that way.
- Dependency versions are pinned exactly. The `@earendil-works/*` packages share one version; change them together, and keep them at the version of `@vzlentin/harness`. In the root package they are plain `dependencies`. A global install has two copies of each, one under harness and one under workflows, and the host loads both: the entry of workflows uses its own copies next to harness's, so the versions must stay equal.
- workflows has no copy of harness: a global install uses the global `@vzlentin/harness` next to it. `@vzlentin/harness` is an optional peer dependency at a caret range, which `src/harness.ts` reads from `package.json`, and a devDependency at an exact version in that range for the checkout and the tests. Import its modules as `@vzlentin/harness/<module>`. Vitest inlines harness (`vitest.config.ts`).
- `src/cli.ts` checks harness before it imports `main.ts`, so no static import of `cli.ts` may import harness. `src/harness.ts` finds harness by reading the `node_modules` folders, not through Node's resolver, which keeps a failed lookup, so an import after a harness install in the same process works.
- `src/setup.ts` is the setup of a top-level global install: it installs a missing harness into the prefix of the install under harness's install lock (`src/install-lock.ts`, a copy of harness's `pi/install-lock.ts` that takes the lock folder as an argument), runs harness's setup with the Pi package `@vzlentin/pi-agents`, sets the `workflows` entry, and runs harness's setup with the Pi package `@vzlentin/pi-workflows`, which installs it from npm unless Pi already lists it. `scripts/postinstall.js` (plain JavaScript, as Node does not strip types under `node_modules`) runs it when npm runs install scripts, and the installed command runs it on each start, since npm 12 runs no install script by default; it stays cheap because harness's `setupOnce` keeps a stamp for each package path and version. A Pi failure is a warning, and the postinstall never fails the install: a failed global install of a new package leaves its `bin` link pointing to nothing.
- The CLI is a client of the harness host, and sets the entry `workflows` in harness's `entries.json` (`ENTRY` in `src/harness.ts`: `dist/entry.js`, or `src/entry.ts` in a checkout) before it can start a host.
- `pi/index.ts` runs inside Pi. Pi supplies `pi-ai`, `pi-coding-agent`, `pi-tui` and `typebox`, so they are `peerDependencies` at `"*"` in `pi/package.json`. It waits for the install lock (`pi/install-lock.ts`), finds the global workflows install (the first `workflows` on `PATH`, else `npm root -g`), and runs its `dist/cli.js` with the Node of Pi as a child process; it imports nothing of the package. Without an install, the tool and `/workflows` give the install command, and a TUI session offers to install it; `pi/install-lock.ts` takes, releases and waits for the install lock. In a checkout, run `npm run build` and `npm link` before `pi install ./pi`.
- Never verify with a real `workflows` run. It spends model calls, and inside a ship run it starts another run.

## Engine and workflows

- `src/` is the engine: run directories, the script task, sessions, turns, retry, resume, Git repository selection, prompts, and `meta.ts`, the generic entry point that runs any workflow script as `workflows <wf>`. A run executes in the harness host of its project: `src/entry.ts` is the entry that the host loads (from harness's `entries.json`), and it gives the host the script task. The CLI in `main.ts` is a client: it prepares the input, writes `runs/<id>/project`, sends `start` with the key `wf:<run ID>#<n>`, and follows the run with `wait-task` while it polls the progress documents in the project store read-only. `task.ts` holds the script task and its checkpoint; its saved input is `ScriptInput` of `meta.ts`. `script.ts` holds the script calls and sessions, which are children of harness's children library, opened with a task owner whose group is the run ID, keyed `wf:<run ID>/<call key>`. `run.ts` holds the run ID, `UsageError`, `Run` and `Io`. `run(name, args)` in a script starts a child run with its own run directory, as a pi-durable child task of the caller's task. The caller waits for the child task with `waitForTask`. A failed phase commits a `failed` outcome, so the waiter of a child or root task sees the failure in the task's outcome.
- The workflows are data: `workflows/*.js`, `prompts/*.md` and `agents/*.md`. There is no workflow in TypeScript.
- A workflow script declares its description, arguments, worktree and exit codes in `export const meta = { ... }`, a literal object at the top. It returns its report lines as `result.report`.
- `optimize` is the workflow script `workflows/optimize.js`: it evaluates each candidate with `run("ship", ...)` child runs, and reads and writes files through `sh`.
- `ship` is the workflow script `workflows/ship.js`: its `meta` gives the work item, the rounds and the worktree, and the script is the child runs `workflows/rpi.js` (research, plan, implement, one commit), `workflows/review.js` (the review loop, which owns `rounds`) and `workflows/judge.js`, then the squash and the report lines. Each also runs on its own (`workflows rpi`, and `workflows review` and `workflows judge` on the branch of the current directory), and `campaign`, a queue of ships, ends with `judge.js` on the change of all its items.
- `src/lib.js` is the script lib: plain JavaScript that the prelude of `script.ts` gives every script (`subjectOf`, `memory`, `commitAll`, `diffStat`). It runs in the sandbox, so it uses only the script calls. The build copies it to `dist/`; declare each helper in `workflows/script.d.ts`. Put a helper that two workflow scripts need here, not in each script.
- `status(text)` in a script sets the short status of its run, which the Pi widget shows for a background run after the statuses of its callers (`item 2/5 › round 1/3: review`). Give a new long-running workflow script statuses.
- `src/entry.ts` also gives every conversation of the host the `workflow` tool, which runs the CLI of the same install as a child process with `HARNESS_PROJECT` and `PI_SESSION_ID` set. The run saves `PI_SESSION_ID` as `parent`, and `sessionOf` in `script.ts` opens the sessions under that conversation and removes the tool's extension from them. With `background`, the tool returns `started`, the input gets `notify`, and `notify` in `task.ts` posts the outcome to `parent` at each end of the task, with the request ID `workflows.result:<run ID>/<task ID>`.
- Every script run is the task `workflows.run`, `scriptTask(host)` in `src/task.ts`, whose name and version are `TASK`. Bump `TASK.version` when the shape of its saved input changes.
- A run has one live task at a time. Start, resume and wait share one way to follow a task. `resume` follows the run's last task when it has not ended, and starts a new task with the same input when it ended without completing. Keep a new kind of run on that path. A child run is not a run of its own: `list` and `resume` see only root tasks. A failed task, root or child, ends as `failed`. The saved calls of a script are session-scoped documents of the store, keyed `<run ID>/<call key>`, so they stay after the task ends; a `run()` call creates a new child task with the input of a child task that ended without completing. Each call document records the call's kind, args, phase, start and end times, and its result or error; only a saved `result` replays. `show`, `list` and `save` in `main.ts` read these records and the root tasks from the project store file, with no Harness and no host, through `src/store.ts`, which opens the file read-only so the CLI takes no lock that the host waits for and runs no checkpoint.
- The end of a run ends its sessions (`endSessions` in `task.ts`): a completed run closes them; a failed or aborted run closes only what is under them and aborts the turns of the sessions that an earlier task of the run opened, which pi-durable's abort of the current task does not reach.
- Ctrl+C detaches the CLI and the run goes on in the host. A second Ctrl+C while the CLI follows a run that it started or resumed, also one that came before the window of `STOP_WINDOW_MS` opened, or `workflows stop`, sends `abort-task`. `CtrlC` in `src/run.ts` counts the presses, and the tests press through the same class.
- When the script ends, `runScript` cancels the host calls that still run and waits for them, so the end of a run comes after its last call.
- Every `start` sends `version: TASK.version`, so a host that loaded another version of workflows refuses before it creates a task. A command that follows a task it did not start compares `TaskInfo.version` with `TASK.version`.
- Biome does not format `workflows/*.js`: a script body has a top-level `return`. oxlint lints them.

## Durable runs

- Saved runs in the project store resume against the code that the host loaded. When you change the shape of the stored input or the checkpoint, bump `TASK.version` in `src/task.ts`. Only a task at exactly `TASK.version` resumes: a run saved by an earlier or a later version cannot resume, and the host leaves it pending.
- The harness host lock covers the store; workflows has no lock of its own.
- A phase can rerun after an interruption or a failure. Keep Git steps safe to repeat, and keep each turn request ID unique in its session: an answered request ID returns its saved answer, and a failed one is sent again under the next free ID. An answer that stopped for a reason other than its end or a tool call, such as its length, counts as failed.
- A workflow script also runs again from the top at resume. Keep its `sh` and `ok` Git steps safe to repeat: a step whose result was not saved runs again.
- A run saves its prompts and models before it starts. Prompt or model edits change only new runs.

## Prompts

- Keep the frontmatter and the last line `$@` in `prompts/*.md`. `instructions()` removes them.
- The SHIP or FIX answer rule and the evidence rule of the review challenge are in `workflows/review.js`. Do not move them into a template.
- The judge answers the eight numbered questions of `prompts/judge.md` through `respond`, in question order, and `score()` in `workflows/judge.js` reads them. Keep the numbering and the meaning of questions 1 and 2.

## Tests

- Tests must not call a real model, a real `gh`, a real `npm`, or the user's Pi or Git configuration. Use `sandbox()` and the faux provider in `test/support.ts`. Each `workflows(...)` call of a test runs an in-process harness host with its own fake model, which loads the entry of this checkout from harness's `entries.json`, and closes it when the command ends, as a host stop does.
